## 2. 关键取证: TCP guest→host 数据段在 QEMU 9.2 slirp 被丢弃

**evidence chain**:
1. TCP client 状态机 (SYN→SYN-ACK→ACK/PSH) 全对: SYN 到达 host (server accept),
   SYN-ACK 回到 guest (flags=0x12 收到), **get 数据段 tx rc=0 (QEMU 处理)**;
2. **但 host server recv 永不到数据** (超时→FIN; guest 收到 FIN flags=0x11);
3. 16B 纯数据段同测相同结果 (排除 cksum/HTTP 格式; **cksum 计算版 SYN 通 =
   cksum 算法正确**);
4. cksum=0 实验: **SYN 也被拒** → slirp 校验 TCP cksum (UDP cksum=0 合法,
   **M124 UDP 双向已验证 PASS**);
5. 差异面收窄: guest→host 的 **TCP 数据段** (有负载) 未转发, SYN 通;
   m125 (host→guest, hostfwd) 数据段通 —— 方向不对称。

**结论/处置**: QEMU 9.2 slirp 对 guest 出站 TCP 数据段的转发限制 (未进一步开
源码定位; 记录为 W21 后续/或 QEMU 版本演进); **闭环传输通道用 UDP (M124 已证
双向 + 校验=0 合法), TCP 服务器完整性由 m125 (hostfwd 入站) 承担**; TCP 客户端
数据面列为 W21-followup (QEMU 源码 slirp/tcp_input 查证 or KVM 对比)。

## 3. 踩坑

1. **tcp_cksum 伪头缓冲越界**: ph[40/48] 对 47B GET 段 (tlen=67) 越界写 31B →
   用户栈破坏 → #GP rip=字符串 ("1.0\r\nHo") — m139 早期崩溃根因; ph 需
   12+tlen 上限 (m125 同源隐患记录);
2. **fujo_net_tx ring 写死位置**: 二次发送覆盖 ring[0] → tx 永久超时
   (m139 "get rc 不返回"假象); 修复 = ai%VQ_SIZE 定位 (影响所有多包发送);
3. **initial SYN 缺失**: client 握手第一步没发 (写 demo 时忽略) → 服务器
   accept 不存在/请求诡异; 状态机每分支回归前先列出全部发送点;
4. **QEMU sendkey 长序列易错**: 路径键缺 slash → shell 解析成多 token
   ("runfile /tmp /hello"→ 打开 /tmp 目录 = empty) — fujoregress keys 逐段
   与 shell 回显核对。
