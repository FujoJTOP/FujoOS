# 07 · AI OS 愿景：究竟是什么让 AI OS 能够真正实现

> 状态: 观点草案 (v0.1) · 讨论入口: [Issue #1](https://github.com/FujoJTOP/FujoOS/issues/1)
> 本文是 FujoOS 的立场文件，也是 M9 之后功能设计的上游约束。

## 0. 一句话立场

**AI OS 的真正门槛，不在"模型住在哪一层"，而在"模型被调用时，OS 手里握着什么、能给什么"。**

## 1. 反命题：为什么"把模型塞进内核"不是答案

现阶段行业现实（我们接受其为设计输入）：

- 任何模型（哪怕 0.5B 的小模型）都在用户**启动 agent 之后**才被调用；
- 模型是被调用的服务，不是环境传感器；
- "常驻小脑"式的内核内嵌模型在当前技术阶段既无必要也无收益。

由该现实推出的推论：**OS 的机会不在"模型常驻"，而在"调用发生的环境"**。模型调用时机由 agent 决定，那么 OS 应该把"调用前、调用中、调用后"三个阶段的环境做成一等公民。

## 2. 充分必要条件：AI OS 四件套

### 2.1 模型调用原语 —— 模型是 OS 的一等资源

```
fujo_model_call(prio, ctx_ref, request) -> response
```

- 系统调用级特权：由内核调度模型调用的优先级、额度与生命周期；
- **权重即虚拟内存对象**：大模型权重按层按页映射、页错误驱动流式换入——冷启动不是"加载 30GB"，而是按需分页（我们已具备恒等映射/分页基础设施）；
- 本地小模型与远端大模型的闸门由同一原语统一管理；
- 与"应用内模型"的分界：OS 保证"随叫随到"（页缓存预热、优先级、带宽调度）。

### 2.2 Agent 是一等进程 —— 不是聊天窗口

Agent = 容器态生命周期 + 会话上下文 + 工具集 + 能力权限。在 FujoOS 中：

- 容器即 `.run`（FUJR 容器：清单 + 代码单元 + 依赖 + 签名）；
- Agent 实例 = 可迁移、可恢复、可审计的带权限进程；
- 生命周期：启动 / 热恢复 / checkpoint / 资源优先级——与普通进程同等表达。

### 2.3 上下文即服务（fujoctx）—— OS 唯一能给而应用给不了的东西

当前 agent 的瓶颈不是模型不够大，而是**拿不到机器的态**：屏幕、窗口、文件、日志、最近系统调用。设计：

- `fujoctx`：系统服务，把机器状态**结构化、零拷贝**地交给模型消费者（共享内存环形缓冲 + 订阅事件）；
- 注入面（首刀）：窗口与焦点状态 / 键盘与输入轨迹 / 最近 `.run` 装载记录 / syscall 摘要 / 文件变更；
- 边界：只经由能力句柄授权；本地只出摘要，敏感内容不出域。

### 2.4 权限与审计 —— 可解耦的护栏

- 模型输出永远是**提示**，不是**决策**；
- 每次模型驱动的行为走能力句柄模型：最小权限、可审计、可回滚；
- 错误预算：模型错了 → 性能回退，而非故障。

## 3. 双脑 Split（行业现状修正版）

不是"常驻小脑+按需大脑"，而是：

```
agent 启动
   └─ 本地小模型（第一道闸, 100ms 级, 离线）
        ├─ 意图分类 / 参数抽取
        ├─ 工具候选选择（能力句柄权限域内）
        ├─ 上下文摘要与隐私过滤（留在本地）
        └─ 低置信度 -> 升级: 本地大模型(按页流式) 或 云端
```

- 小模型 = 调用链路第一环的确定性闸门，生产可依赖（延迟、隐私、离线可得）；
- 大模型仅在升级路径被激活；
- "小模型辅助大模型"的准确含义：**闸门**，而非**哨兵**。

## 4. 工程原则（M9 及其后不可违背）

| 原则 | 内容 |
|---|---|
| 不阻塞内核路径 | 模型服务 ring-3；内核只订阅结果，任何预测性用途不允许同步依赖 |
| 失效降级 | 模型结果永远是提示；错误 = 性能回退，不是故障 |
| 权重流式 | 大模型权重 = mmap 对象；页错误驱动，避免整体加载 |
| 隐私边界 | 本地小模型处理私有数据；出域只传摘要/置信度 |
| 可测 | 每个模型接入点必须给出"基线 vs 模型"的对照指标（延迟/命中/误报） |

## 5. M9 里程碑切片（首个闭环）

**"Agent 启动 → 本地小模型意图分类 → 工具路由 → 容器执行 → 终端回显"**

> **状态（实验分支 `fujoos-ai-dev`，v0 已落地）**：
> ① `fujonn` 服务骨架 ✅ —— 内核 `ai.rs`：`fujo_ai_classify`（0x5101）+ `fujo_ai_fetch`（0x5102，fujoctx 注入）两个宏原生原语，ring3 可调；规则引擎占位（**NN 接入点注释就绪**，接口稳定）；
> ② Agent 运行时 v0 ✅ —— `sdk/ai/agent.c`：命令槽（0x402000）读取 → 模型原语调用 → 上下文注入 → 计划输出 → exit；
> ③ Agent 宿主 ✅ —— 主流程键盘命令捕获（sendkey 注入）→ 意图槽 → 启动 agent；
> ④ 实测链路（QEMU）：`m9 : agent cmd='run'` → `ai : classify('run') -> RUN [engine=rules]` → `agent: fujo-agent up / model_call / context[...] = fmt=pe;win=2;mod=agent;keys=1` → exit 内核接管；
> ⑤ **已知实现项（低优）**：ring3 侧对 0x5101 返回值的接收存在偏移（内核侧返回值已验证 1）；接口契约与调用链已验证，问题在实现的接收侧，接入微型神经引擎前优先修正。
