# 74 · W20 — 脱 QEMU 专属: 平台审计 + 检测原语 (m133)

> 里程碑: W20 (新方向第一波) · 上游: 用户指示"不再是 QEMU 专属操作系统"
> 一句话: **平台差异审计全表 (QEMU 宽松语义 vs 真机规范语义) + `platform.rs`
> 检测原语 (Bochs VBE 0xB0C5 证据链) + LAPIC ICR 投递双语义运行时切换 ——
> 首个被证明的 QEMU 差异 (ICR) 已按平台路由 (m133 PASS)。**

## 1. 动机与核心发现

QEMU TCG 是**宽松仿真器**: 它对部分硬件的模拟行为与 Intel 规范/真机相反。
本内核 W17b 实证了第一个: **LAPIC ICR 投递触发点**。

| 语义 | QEMU 实测 (W17b) | Intel SDM 10.5.2.2 (真机) |
|---|---|---|
| 写 0xFEE00300 (低 32 值) | **触发投递** (用已存高 32 dest) | 仅存储, 不投递 |
| 写 0xFEE00310 (高 32 dest) | 仅存储 | **触发投递** (用已存低 32 值) |

后果: 按 QEMU 习惯写"低先高后" → INIT 投给 dest=0 (BSP 自身) → **BSP 被 INIT 复位冻结**;
按 Intel 习惯写"高先低后" → QEMU 下 INIT 语义正常但真机根本不投递。
**同一段代码在两个平台行为相反** —— 这就是"QEMU 专属"定义, 也是可靠性风险的来源。

## 4. 真机引导路径 (multiboot v1 + GRUB2)

内核镜像本身是标准 multiboot v1 (MB_HEADER @ 前 8KiB, flags=0x10003) —— **GRUB2 可直接引导**。

```
# grub.cfg (真机/虚拟机 ISO)
menuentry "FujoOS" {
    multiboot /boot/fujo-kernel.bin
    module /boot/m133.elf
}
```
- 装载范围: 0x100000..0x2C0000 (load_end), 入口 0x101000; GRUB 精确遵守 (QEMU 相同装载路径 = 兼容性等同);
- 模块区 (initrd): multiboot module 在第 1 段后 (内核尾部上方), 与 QEMU -initrd 语义一致;
- **W20 二期计划**: 生成引导 ISO (`grub-mkrescue` 或 `isolinux`) + 真机 checklist (COM1 串口捕获 / VGA 文本兜底 / LAPIC MSR 探测)。

### 4b · 视频请求双变体 (W20 三期 A/B 实证)

**QEMU 9.2 TCG `-kernel` 的 multiboot 装载不支持视频请求 (flags bit2)**:
A/B 实验 —— flags=0x10003 无视频 → 正常 boot 56 行 (`fb : no mbi framebuffer`);
flags=0x10007 请求 1024x768x32 (header 12 字段, checksum 复核 sum≡0) → **内核 0 输出**
(QEMU 拒绝/装载失败, 无 guest_errors 记录)。

**决策**: 参考机主镜像保持 8 字段无视频头 (QEMU 兼容); **mbi framebuffer 接收代码
保留** (mbi bit12 一旦出现即接管: `graphics::init` 优先 mbi → `mem::map_phys_identity`
映射任意物理 LFB → SAVE_LFB_OK 渲染)。真机视频变体 = 构建脚本 `--video` 选项把
header flags 置 0x10007 + 按 12 字段重算 checksum (GRUB2 会交付 mbi framebuffer)。

**当前 W20 三期交付**: mbi 解析 (12 字段对齐验证) + 接收 + map_phys_identity (任意
物理地址设备页) + 兜底日志; 回归 25/25 无破坏 (无视频请求路径复现旧行为)。

## 5. 踩坑 (本波)

1. **icr_mode 值域 ≠ is_qemu 布尔**: 0/1 模式码与 0/1 布尔是反的; 断言写 `icr_mode != is_qemu` 直接 FAIL —— 平台字段语义要一一对应再断言 (m133 T2 修正为双分支对齐);
2. **platform 检测必须在 graphics 早期**: `note_vbe_id` 在 `vbe_get(0x0000)` 后立即调用; 若放在 init 末尾, 真机 (lfb=0 return false) 时检测晚于第一次使用;
3. **QEMU 默认 (无证据) 按适配模式**: 保守策略 —— 跳过 VBE 探测直接默认 qemu 会误判真机; 而默认 intel 会让 QEMU 回归崩 (INIT→BSP)。当前"无证据=QEMU 适配"保证参考机 100% 稳定, 真机首个 VBE 探测即修正 (1 boot 内)。
